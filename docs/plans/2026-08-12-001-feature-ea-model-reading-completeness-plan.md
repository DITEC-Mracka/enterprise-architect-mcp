# Reading the EA Model Without Silent Loss - Plan

## Goal Capsule

**Objective.** Make the MCP server return the whole answer, or say that it did not. Today it drops analyst-authored content — the attribute a mapping arrow attaches to, the rule attached to a use case, the tail of a long note, the 1,555 search hits past the limit — and returns a clean, well-formed payload that gives no sign anything is missing. That failure mode is worse than an error: it produced a false "cannot be verified" claim published to a defect tracker.

**Product authority.** The tool surface described here is the contract; the repository owner decides scope changes.

**Open blockers.** None — and after this round none sit inside the work in scope either. R5's dotted-path form had been held out of the first increment on the reading that no rule could resolve it; measurement withdrew that reading, since a path is recovered by matching against the tree's real names rather than by splitting on the separator, which returns the true node every time and uniquely in 78.1% of cases. The form, its acceptance criterion A14, and the ownership question that hung on it therefore close together. Phase 4's question closed with them, by ruling that a question about future evidence gets a dated review rather than an open watch — so nothing in this document is now waiting on a decision. R13's own remaining question is whether it answers a demonstrated need, which is why Phase 4 sits outside the implementation scope, and nothing earlier depends on it. The questions that were open and are now settled by measurement: R3's matching substrate, chosen against three alternatives, and its *scope*, extended to the scenario, constraint and feature text R3 itself names at a cost measured rather than projected; whether that choice should be exposed as a startup parameter, which the measurements answer with no, both substrates returning identical results at equal memory; whether feature links matter on connectors no diagram draws, which they do, at a tenth of all such links; R13's runtime floor, settled at Node 24 LTS, where the type definitions that appeared to force a wider choice are handled by a local augmentation, measured to compile; R13's time limit, which a worker thread cannot enforce and a child process ends in 14 ms; the connection-opening question, which dissolves rather than resolves once the query has a process of its own; and what that process is given, which is a reduced environment and a temporary directory of its own, both measured free. Four more fell in the early increments: how long text is retrieved, which needs no new shape once the longest note in the export turns out to be 24 kB; whether R0's table declaration binds every tool, which it does, no tool returning more than a third of its source table; whether a link target found in note markup may be resolved, which its scheme decides; and how much of the tagged-value store is analyst-authored, which is a low single-digit percentage. Every schema and behavior claim in this document was verified by direct query against a real 663 MB model export and by reading `src/tools/*.ts`, `src/database.ts`, and `package.json`.

**Implementation scope.** Phases 1–3, R11 and R12 are ready to plan and build. **Phase 4 — R13, the guarded query — stays in this document but outside that scope**, at `requirements-only`. The reason is not that R13 is underspecified; its mechanism is settled and measured. It is that R13's last open question asks whether the tool answers a demonstrated need, and the only thing that can answer it is R12 in use — either a reader loses content no typed tool returns, or none does. Building R13 first would settle that question by making it unaskable. R13 is also the only requirement that moves the runtime floor, so holding it back keeps the floor where the pinned type definitions already reach. Every schema and behavior claim in this document was verified by direct query against a real 663 MB model export and by reading `src/tools/*.ts`, `src/database.ts`, and `package.json`.

## Product Contract

### Motivating case

On 2026-08-12 an agent was investigating ZVJS defect #463023 — an electronic submission (*eForm žiadosť o výživné*) whose fields were not being loaded into the FEOO screens. The analyst's comment named the specification: a diagram, `0103 Spracovanie eFORM - žiadosť o výživné`, cited by dotted model path. The question was narrow and entirely factual — **which eForm attribute is supposed to fill which screen field**.

What happened instead:

1. The dotted path resolved to nothing — no tool accepts a path.
2. `ea_search` found elements around the diagram but never the diagram, because it queries `t_object` only.
3. With the diagram unreachable, the agent fell back to `ea_get_connectors` on the element it *could* find (`a7680`) and got five rows carrying only element-level endpoints — four reading `a7680 → Vyživovaná osoba` and one `a7680 → Blízke osoby klienta` — with every descriptive field `null`. Five arrows, two distinct targets, and no way to tell which field went where.
4. From that, the agent concluded the mapping exists only as graphics and **published that conclusion into the work item**: *"⛔ Neoverené: obsah diagramu … mapovanie atribútov je na ňom grafické a cez rozhranie modelu ho nevidíme."*

That statement was false. The mapping is fully relational — it was in `t_connector.StyleEx` all along. The agent was unblocked only when the user supplied a raw GUID and the model was queried by hand with `node:sqlite`, outside the MCP server.

**What the correct answer changed, once it was readable:** the client is identified on the diagram by *základné číslo* (`a7779`), not by birth number, which is what the code was assumed to need; `a7782 → Blízke osoby klienta.Rodné číslo` was confirmed as specified rather than guessed; the address block is genuinely **not** mapped — a real specification gap, now distinguishable from a tooling gap; and `IČO` / `a1011` do not appear on the diagram at all, which removed the basis for one of the points raised against the developers.

**The cost.** A false "cannot be verified" disclaimer in a tracker; questions sent to an analyst that the model already answered; a specification gap and a tooling gap presented as the same thing.

**This is not a one-off, and diagrams are only half of it.** Analysts on this project cite the model in two shapes. One is a diagram carrying attribute-level mapping — the case above, which recurs across eForm processing. The other is a use case reference: `UC_FEO_XXXX krok N`, a named business rule, a logging rule such as `LOG_FEO_083`. In ordinary development the two are reached for about equally often. The tools serve the second no better than the first; the requirements below cover both.

### Problem

The server's failure mode is **silent incompleteness**. Each instance below was verified against the model export named in Provenance.

| Where | What is dropped | Scale in the model |
| --- | --- | --- |
| `ea_get_connectors` | The attribute or operation each connector end attaches to, held in `t_connector.StyleEx` as `LFSP=<guid>L;` / `LFEP=<guid>R;` | 16,392 of 81,973 connectors carry one |
| `ea_get_diagram_elements` | Every connector on the diagram — it joins `t_diagramobjects` only | 106,622 connectors have both ends on a diagram; `t_diagramlinks` indexes only 103,899 of them |
| `ea_search` | Results past `LIMIT 25`, with no total returned | a search for `pohľadáv` matches 1,580 elements |
| `ea_search` | Note text past `substr(Note, 1, 200)`, with no truncation marker | 11,467 elements have a longer note |
| `ea_list_elements` | Results past `LIMIT 50`, with no total returned | — |
| `ea_get_package_tree` | The requested depth is silently clamped to 3, and the 200-package cap is flagged without a total | 10,579 packages |
| `ea_get_scenarios` | The scenario's own `Notes` — selected in SQL, then discarded; and the step attributes `uses`, `useslist`, `result`, `state`, `trigger`, `link` | 4,655 scenarios carry step attributes; 168 carry a non-empty `Notes` |
| everywhere | Character entities are returned raw (`Pr&#225;vnick&#225;`), which also makes `ea_search`'s `LIKE` miss them | 22,421 of 29,146 non-empty element notes (77%) and 27,265 attribute notes |
| everywhere | Embedded links are buried in markup and never surfaced as targets — including `$element://`, `$diagram://` and `$feature://` traces to other model nodes, and `$inet://` references to legislation | 1,111 element notes and 710 attribute notes carry an `<a href>` |
| — | `t_objectconstraint` is not exposed by any tool — use case preconditions, postconditions, and named business rules whose `Notes` hold the specification text | 3,783 rows |
| — | The schema itself is invisible. No tool lists tables or columns, so a caller cannot discover that a field exists — which is precisely how the motivating failure happened: the agent could not learn that `StyleEx` was there | 100 tables; `t_connector` alone has 79 columns |

**The pattern is already solved once in this codebase, and half-solved once more.** `ea_get_element` returns `attributesTruncated` and `attributesTotal` alongside its capped list — the caller always knows whether it has everything. `ea_get_package_tree` gets halfway: it sets a `truncated` flag with an explanatory message, but reports no total and says nothing at all about the depth it silently clamped. Nowhere else is the rule applied. It is documented in [docs/solutions/design-patterns/mcp-tool-inline-detail-with-truncation.md](../solutions/design-patterns/mcp-tool-inline-detail-with-truncation.md); most of this plan is making the rest of the server behave like `ea_get_element` already does.

**A second, independent problem: nothing can be found by the name an analyst uses.** `ea_get_diagram_elements` needs a `Diagram_ID` that no tool returns. `ea_search` covers `t_object` only, so all 9,717 diagrams are invisible. Analysts cite by GUID (`$diagram://{GUID}`), by dotted model path, or by name — none resolve. And names alone are not enough to identify anything in this model: 806 diagram names, 1,111 package names, and 7,566 element names are duplicated.

### Users

AI agents reading an EA model on behalf of a developer or analyst, in workflows where the model is the source of truth for required behavior — defect investigation, handoff authoring, implementation against a specification. The project rule these agents work under requires verbatim citation of the model and forbids asserting anything not actually read, which is why partial-but-unmarked output is a correctness problem rather than a convenience one.

### Requirements

**R0 governs everything below. Every tool states whether its answer is complete, and what the caller can do about it.** A caller must never have to guess whether it is looking at the whole answer, nor infer the remedy from the tool's documentation. The obligation is graded, because the remedy is not always constructible:

1. *Always — machine-readable facts.* Any capped list reports rows returned, total matched, and whether it was capped. Any truncated text is marked as truncated. Any structured value the server chose not to resolve is reported as present-but-unresolved rather than omitted. Alongside the cap, the response names the parameter that controls it — or states explicitly that no such parameter exists. **Every response also names the source table or tables it read and states that it returns a selected subset of their columns, directing the caller to R12 for the full list.** The obligation is the *set* of tables the answer was drawn from, and it is separate from — not satisfied by — the per-field origin described next. The distinction matters because most tools here join: `ea_get_element` reads `t_object` LEFT JOIN `t_package` and returns 13 columns, `ea_get_connectors` joins `t_object` twice for the endpoint names, and `ea_get_diagram_elements` spans four tables across two statements. The table set is declared by each tool rather than discovered at run time. R13's authorizer technique does not reach here: that authorizer belongs to the path running caller-supplied SQL, and installing it on the connection the typed tools share would deny R12's own `PRAGMA` calls — quite apart from R13 being the last requirement in this plan while this obligation binds from the first. What the caller needs from the declaration is to know a table was consulted, so it can ask R12 what else that table holds; that the declaration stays true is enforced by the one-directional `columns()` test in the Verification Contract rather than by review. **Every response also declares, per returned field, whether it carries a stored column value or a derived one.** `StatementSync.columns()` supplies this from the prepared statement itself: a field reading a column reports the table and column it came from, a field computed by an expression reports none. The second case is the one that earns the obligation — `ea_search` returns `substr(o.Note, 1, 200)`, a truncation that no cap and no match count accounts for, and today marking it depends on the tool's author remembering to. Generating the declaration from `columns()` makes the distinction mechanical rather than remembered, which is the reason R0 exists at all. Two limits are measured and stated here rather than discovered later: `columns()` does not distinguish aliases, so both endpoint names in `ea_get_connectors` report `t_object.Name` and the field origin is true but uninformative there; and it describes returned columns rather than tables read, so a statement returning only `count(*)` attributes to nothing while having read a table in full. That second limit is precisely why it cannot supply the table set above. Caps, truncation and unresolved values are not the only way content goes missing: a column the tool's `SELECT` never names is dropped without any of the three firing. `ea_get_connectors` reads 17 of `t_connector`'s 79 columns, and after every phase here it will still omit 31,644 non-empty `Btm_Mid_Label`, 3,284 `DestRole` and 1,552 `SourceRole` — the `StyleEx` failure shape exactly, and A12's remedy is reached only by a caller who already suspects something is missing. Naming the source table is what replaces that suspicion with a fact, and it is the symmetric counterpart to R13's obligation to name the typed tool whose semantics a raw query bypassed. The server always knows its own signature, so this level has no exceptions.
2. *When the continuation is unambiguous — the exact next call.* A structured `{ tool, arguments }` the caller can issue as-is. The test is mechanical: **the server can build the call from its own signature, the arguments the caller supplied, and the identifiers carried in the result it is about to return.** All three parts are needed — a note truncated by `ea_search` is resolved by `ea_get_element` on an id the caller never supplied, and an R5 candidate's id is wholly result-derived; only the raised-limit case is constructible from caller arguments alone. That covers a truncated note resolved by `ea_get_element` on the same id, a ranked candidate from R5 resolved by id, and — the most common incompleteness in the whole server — a capped list continued by the same call with a raised `limit`. A search matching 1,580 and returning 25 is a level-2 case, not a level-3 one: the server wrote the cap, so the server can write the call that lifts it.
3. *When it is ambiguous or absent — a text hint and nothing more.* A package tree whose depth was clamped says to call again with a specific `packageId`, because which sub-package to descend into is the caller's choice and not derivable from the arguments already given; an unresolved feature link says no continuation exists. No fabricated call.

**R13 is never the continuation the server proposes for another tool's incomplete answer.** The level-2 calls offered by the typed tools are typed-tool calls; R13's own row cap is continued by an R13 call with a raised limit, per A13, exactly as any other tool's cap would be. A server that answered "your list was capped, here is a query for the rest" would hand per-table semantics back to the caller at the exact moment the answer was known to be incomplete — the cost recorded in the Key decision beginning *The typed tools are the answer…*. R13 stays available to a caller who reaches for it; the graded remedy above is unaffected by its existence.

The hard rule across all three: **never offer a call the server cannot honour.** `ea_get_element` today accepts only `elementId` and caps attributes and operations at 50 with no way to reach the rest — under level 1 it must say the cap exists and that no parameter controls it, rather than inventing a paging argument that would fail.

**All model-authored text is untrusted content.** Every note, scenario, constraint, name and identifier the server returns was written by whoever held write access to the export, and the consumer is an automated agent that acts on what it is handed. This plan's whole effect is to move much more of that text into such an agent's context — full untruncated notes, scenario notes and step attributes, `t_objectconstraint` specification text, and under R13 arbitrary column values. The server returns all of it as data, labelled as model content, and never elevates any of it into instruction or presents it to the consumer as such. R3 reaches this conclusion for link targets specifically; the rule belongs at this level, where every tool inherits it the way it inherits completeness reporting.

#### Phase 1 — stop losing data

**R1. Feature-level link resolution on connectors.** `ea_get_connectors` returns, for each connector, the attribute or operation each end attaches to. Source of truth is `t_connector.StyleEx`: `LFSP=` for the source end and `LFEP=` for the target end, each followed by a braced GUID and, usually, one trailing letter. That letter belongs to the style token rather than the GUID and must be stripped before lookup — but it cannot be stripped as a literal, because it records which side of the feature's own element the arrow meets and so does not follow the key. `LFSP` ends in `L` 14,484 times and in `R` 1,176; `LFEP` ends in `R` 9,290 times, in `L` 1,145, and carries no letter at all 147 times. Matching the braced GUID by shape and discarding whatever trails it is correct for all 26,242 ends in this export, whereas removing a literal `L` after `LFSP` would corrupt 1,176 GUIDs and leave 147 more unmatched. GUID comparison is case-insensitive, and **the case-insensitivity is written as `ea_guid = ? COLLATE NOCASE`, never as `UPPER(ea_guid) = UPPER(?)`**. Both forms are correct and only one is usable. `t_attribute` carries a unique index on `ea_guid` over 82,337 rows: the collation form searches it in 0.14 ms, while wrapping the column in `UPPER()` makes it unusable and falls back to a full scan at 17.12 ms — 143 times slower, paid once per connector end. Measured end to end, that is the difference between a mapping diagram assembling in 3 ms and one measured at 11,492 ms. Resolve against `t_attribute.ea_guid` first, then `t_operation.ea_guid` — an arrow may terminate on an operation rather than a field. Each resolved end carries at least name, owning element name, and `Notes`; `t_attribute.Notes` holds the human-readable field description and is what turns the output into a mapping table rather than a list of codes. Per R0, a token that is present but does not resolve is reported as such. **Feature links are not a diagram phenomenon, and the resolution must not be scoped as though they were.** Of the 16,392 connectors carrying these tokens, 1,920 appear on no diagram at all; their ends resolve at 99.5% against 99.7% for the drawn ones, which is 2,778 resolvable ends and 10.6% of every feature link in the export, concentrated on `Dependency` and `Realisation`. Resolving feature ends only for connectors reachable through a diagram would drop that tenth silently.

**R2. Connectors on a diagram.** `ea_get_diagram_elements` returns the connectors drawn on the diagram alongside its elements, carrying R1's feature resolution. One call on a diagram then yields the complete mapping table. **The worst case in this model is 137 kB of JSON**, measured by assembling the full payload for the heaviest diagrams rather than estimating from counts: `Mapovanie FEOO - MD - Aktualizovaný` at 110 elements and 114 connectors, ahead of the densest-by-connector diagram (250) and the largest-by-element one (207), because payload follows note text rather than either count. The connector list is therefore returned whole and no cap is imposed on it; R0's reporting is what covers a future export that outgrows this.

**`t_diagramlinks` is an incomplete index and cannot be the sole source.** EA writes a row there only when a link carries custom geometry or style; an ordinary connector between two elements that are both on the diagram is drawn without one. Across the whole model, 106,622 connector-diagram pairs have both endpoints on a diagram and **2,723 of them (2.6%, spread over 1,157 of the 8,094 diagrams carrying such a pair) have no row in `t_diagramlinks`**. 116 of those diagrams have no row in that table at all, so a reader treating it as the source sees a diagram with no connectors whatever rather than one with a few missing. The source of truth is therefore the union: rows in `t_diagramlinks` for the diagram, plus connectors whose source and target objects both appear in that diagram's `t_diagramobjects`. The union also covers the 2,745 connector-diagram pairs recorded in the links table whose endpoints are not both present — if the links table says a connector is drawn, it is returned. Both directions are counted over distinct connector-diagram pairs rather than raw rows: `t_diagramlinks` holds 106,681 rows over 106,644 distinct pairs, and a join written without that distinction double-counts 37 of them. Connectors marked `t_diagramlinks.Hidden = 1` (9,855 rows) are returned with a `hidden` flag rather than filtered out; what EA means by that flag is unverified, and dropping them silently would be exactly the failure this plan removes.

*Testing note:* the motivating diagram happens to be complete — 23 implied connectors, 23 link rows — so a single-diagram test would not catch this.

**R3. Readable text without losing what the markup carries.** EA stores `Note`, `Notes`, scenario text, and constraint text as a narrow HTML dialect. The requirement has four parts, and the distinction between them is the whole point.

*Decode character entities, not structural escapes.* `&#225;` → `á` is required — it affects 22,421 element notes and 27,265 attribute notes, and it is why `ea_search`'s `LIKE` misses a query typed in natural Slovak. But `&lt;`, `&gt;` and `&amp;` are **correctly escaped literal text and must stay escaped**: the model uses them for UML stereotype notation (`&lt;&lt;modul&gt;&gt;` = `<<modul>>`) and for operators inside specifications (`Dátum spracovania &lt;&gt; null`). Decoding those in a field the consumer treats as HTML deletes the content from the rendered result — the same silent loss this plan exists to remove, introduced by the fix for it.

*Fold case over the full alphabet, not just ASCII.* Entity decoding is only one of the two reasons search misses. SQLite's `LIKE` folds case for ASCII alone, so `'PRÁVNICKÁ' LIKE '%právnick%'` returns zero while its unaccented equivalent matches. **7,858 element names contain an uppercase Slovak diacritic**, and analysts write module and use case names in caps. Matching is case-insensitive across the whole alphabet the model uses.

**Neither half of this can be expressed in the query.** SQLite's built-in `upper()` and `lower()` fold ASCII only, so no rewriting of the `LIKE` clause reaches `Ľ`; and the decoded form of a note exists nowhere in the file, so there is nothing stored for a query to match against. `ea_search` therefore matches over text the server has already decoded and folded, not over the column as stored. Because no SQL predicate can be written against the decoded, folded form, nothing narrows the candidate set beforehand — every option is either a scan or an index the server builds itself. **The mechanism is settled: a folded corpus held in memory, built on the first search rather than at startup.** Four substrates were measured against one another; both the numbers and the method are recorded in Provenance, so that a future change is compared rather than argued. That measurement also settled how bad today is: across eight representative queries `ea_search` returned the correct count **zero times** — 148 of 7,435 for `ziadost`, 0 of 151 for `PRÁVNICK`, and 1,565 of 2,472 for `pohľadáv` typed correctly in Slovak with its diacritics intact.

*Keep the markup and declare the type.* The dialect is small and content-bearing: 4,050 notes use `<li>`, 3,838 `<ul>`, 321 `<ol>`; there is not one `<table>`, `<img>`, `<div>`, `<span>` or script tag in the model. List items carry distinct conditions — flattening them to plain text runs separate rules into one sentence. Every text field the server returns declares whether it is plain text or this HTML dialect, and that contract is asserted in tests. Stripping markup is a non-goal.

*Surface embedded links as structured targets alongside the text.* 1,111 element notes and 710 attribute notes contain an `<a href>`. The majority are model-internal traces — `$element://{GUID}`, `$diagram://{GUID}`, `$feature://{GUID}` — directly resolvable by R5, plus `$inet://` references to legislation on slov-lex that ground a requirement in law. A reader that only sees anchor text loses both. External `file://` and UNC targets exist but are marginal (101 of the 2,751 anchor targets in the census below) and are returned as-is, not followed.

**Every surfaced target carries its scheme and its resolvability class, and the classification is closed by default rather than by enumeration.** `$element://`, `$diagram://`, `$feature://` and `$package://` are the model-internal set, resolvable by R5. **Every other target is external** — returned as written, marked external, never followed and never validated by the server. That includes bare `http://` and `https://`, `$inet://`, `file://`, UNC paths, `$matrix://`, and targets carrying no scheme at all; an unrecognised scheme classifies as external, never as unclassified. A closed enumeration would not hold: a census of every element and attribute note containing an anchor returns 2,230 `$element`, **234 bare `https`**, 97 UNC, 83 `$inet`, 35 `$diagram`, 18 `$feature`, 18 `$package`, 18 with no scheme, 10 bare `http`, 4 `file` and 4 `$matrix` — so the single most common external form in the model is one an enumerated list built from the obvious cases does not name. The distinction is not cosmetic — a link target is model content authored by whoever had write access to the export, and the consumer here is an automated agent that follows what it is handed. A target it cannot classify is a target it will eventually fetch.

**R4. Diagrams an element appears on.** `ea_get_element` reports which diagrams the element is placed on, via `t_diagramobjects`. This is the cheapest discovery path: an agent that found an element by name reaches its diagram without knowing the diagram exists.

#### Phase 2 — one way in

**R5. One reference resolver.** A single tool accepts the reference forms analysts actually use and returns ranked candidates. Each candidate reports what it is (diagram, element, package, connector), its ID, and its full package path. It is one tool rather than three because the duplicate-name counts above mean every form must return a candidate list with path context anyway; splitting by input form would give the agent three tools with one return shape and a decision it should not have to make. **The dotted path is one of those forms from the first increment, and it is resolved by matching against real names rather than by splitting on the separator.** EA writes `.` between levels, but 1,308 package names contain a dot of their own and only 493 of those are the numbering form a splitter could learn, so splitting is the wrong operation on this model. The resolver instead walks the package tree from each root and, at each level, admits a child whose name is a prefix of the unconsumed remainder followed by a separator, backtracking when a branch fails and emitting a candidate wherever the remainder equals the name of a node in the package it reached. Measured by inversion over 800 nodes — canonical path composed, then handed back — this recovers the true node every time and returns it alone in 78.1% of cases, the rest arriving as two to five candidates. The caller's stated kind absorbs nearly all of the remainder: of 154 ambiguous diagram paths in a 500-diagram sample, 152 hold exactly one diagram. What survives that lands in the ranked candidate list this tool returns regardless of input form.

**The first increment covers an EA GUID in brace form and a plain name.** Those are the two forms the acceptance examples exercise, and both are unambiguous to parse. The dotted model path is deliberately not in it: its tokenisation is unresolved (see Outstanding questions) and blocking the resolver on that decision would withhold the two forms that already work.

**R6. Full package path on every result.** Every result that names a package carries the complete path, not the immediate parent. With 1,111 duplicate package names, a single segment cannot identify a location. This is a field on existing outputs, computed once by recursive traversal of `t_package.Parent_ID` — not a separate capability.

**R7. List and search diagrams.** Diagrams are listable from `t_diagram`, filterable by package and by name substring, returning at minimum `Diagram_ID`, name, type, package path, and `ea_guid`.

#### Phase 3 — the other citation shape

**R8. Addressable, complete scenario steps.** `ea_get_scenarios` numbers the steps so that a citation of the form *krok N* can be resolved directly, and returns every attribute the model records on a step — `uses`, `useslist`, `result` (singular, as the model stores it), `state`, `trigger`, and `link`, the last being the trace from a step to another element. The scenario's own `Notes` is returned rather than discarded.

**What that costs today is measured, because the requirement reads as tidiness until the figures are attached.** Across 4,721 scenarios the model records 16,861 steps, and `ea_get_scenarios` keeps `name`, `level` and `guid` from each. Of what it drops, **`link` carries a target GUID on 1,262 steps** — a trace from a step to another element, the same class of cross-reference R1 and R5 exist to preserve, discarded silently by a shipped tool. `uses` names another use case on 273 steps in the analysts' own citation form, one reading `U_FEO_037: Nástup cudzinca do práce bez ID SP`; `useslist` carries the matching GUIDs on 204; `result` on 142. `state` is populated nowhere in this export, so returning it costs nothing and guards against an export where it is not empty. `trigger` is present on every step. And `t_objectscenarios.Notes` — 168 rows, 425 kB, the longest 11,868 characters — is already named in the tool's own `SELECT` and never reaches the response, which makes it the cheapest correction in this plan and the clearest instance of its subject: the query was right and the answer was short, with nothing in it saying so. The R0 column census scored this tool the *narrowest* gap in the server at 43% unreturned, which is why the figures are recorded here — the proportion of unreturned columns did not predict the value of what was lost.

**Numbering is scoped to a scenario, not to an element.** 1,081 elements carry two or more scenarios and one carries 19, so *krok 2* on a use case with a Basic Path and three Alternate paths names four different steps. Every step therefore carries the name and type of the scenario it belongs to, and a bare *krok N* against a multi-scenario element returns all matching steps rather than picking one. An analyst writing `UC_FEO_XXXX krok 2` usually means the basic path, but the tool does not guess on the reader's behalf.

**R9. Deterministic scenario order.** Scenarios are returned in the model's own order. Ordering by `ea_guid`, as today, is arbitrary — Basic Path is not guaranteed to come first, and multiple alternate paths arrive shuffled.

**R10. Constraints and business rules.** An element's constraints from `t_objectconstraint` are readable with their type and the `Notes` text that carries the actual specification. They hang on `ea_get_element`, not on `ea_get_scenarios`: **161 elements carry 304 constraint rows and have no scenario at all**, and against those `ea_get_scenarios` returns "No scenarios found" and stops — a reader following the citation would conclude the rules do not exist. The model holds 2,117 pre-conditions, 1,169 post-conditions, 279 invariants, 210 of type `Process` — the last being where named business rules live — and 8 rows in two rarer post-condition variants. Verbatim from the model:

```
UC_FEO_2027: Vyradenie spisu po lehote uloženia
  [Process] Pravidlo nastavenia auditovanej činnosti
    "Ak pracujeme s objektom Finančný spis, tak zaloguj LOG_FEO_083: ZMENA_FS_VYRADENIE…"
  [Pre-condition] Spis je v stave uzatvorený
  [Pre-condition] Spis má dátum vyradenia podľa lehoty
```

**Scenario steps reference constraints by name, so the two are not separable.** Step 2 of that same use case reads *"Systém zobrazí všetky záznamy spisov podľa vypočítavanej hodnoty Dátumu vyradenia spisu podľa constrains: Spis má dátum vyradenia podľa lehoty."* — a step that cannot be acted on without the constraint it names, which today no tool can retrieve. This is the level at which the analysis team specifies logging and validation behavior.

#### Phase 4 — reaching what the typed tools do not cover

**R13. A guarded read-only query.** A tool accepts one SQL statement and returns its rows. This exists because every table this plan defers — `t_xref` (131,844), `t_document` (2,841), tagged values (387,280), connector role and label fields — otherwise reproduces the motivating failure shape: the data is in the model and nothing will hand it over. Paired with R12, an agent that suspects the model holds an answer can confirm or refute that itself instead of reporting that the tooling cannot see it.

**One statement means one statement, and a second one is refused rather than dropped.** `node:sqlite` compiles only the first statement of a submission and discards the rest without an error: `prepare("SELECT 1 AS a; ATTACH DATABASE 'x.db' AS x;")` was measured returning a clean `{a:1}`, with the trailing text neither executed nor reported and the authorizer never consulted about it. That is this plan's own damage class — a well-formed answer over an input that was silently truncated — and it is not one of the caps below, because nothing was capped. A submission containing more than one statement is therefore refused with an error naming the text that would have been discarded. It also makes the refusals below order-independent: without this rule a leading `ATTACH` is refused while a trailing one is silently ignored, and a test written the obvious way passes over unverified behaviour.

**Detecting the discarded text needs no SQL parser.** The compiled statement reports the text it actually consumed, and the remainder of the submission is what the server refuses: `prepare("SELECT 1 AS a; ATTACH DATABASE 'x.db' AS x;").sourceSQL` was measured returning exactly `"SELECT 1 AS a;"`, leaving `" ATTACH DATABASE 'x.db' AS x;"` as the tail. Because the split comes from SQLite's own tokenizer rather than from scanning for a semicolon, it is correct on the case that defeats string inspection — `"SELECT ';' AS a; DROP TABLE t_object"` consumed `"SELECT ';' AS a;"` and left `" DROP TABLE t_object"`, with the semicolon inside the string literal not mistaken for a separator. This matters because R13 rejects statement-text parsing everywhere else, and a rule it could only satisfy by parsing would be a rule it could not keep. **A tail consisting only of whitespace and comments is not a second statement**: a trailing `;` leaves an empty tail, but `"SELECT 1 AS a ; -- comment"` leaves the comment in the tail and must not be refused.

**The tool declares itself a fallback, in the place the caller actually reads.** A single tool taking arbitrary SQL is the easiest thing on this surface for a language model to reach for: one signature, no rules to learn, and it appears to subsume the other eleven — the seven typed tools registered today plus the resolver, diagram listing, provenance and schema tools this plan adds. Nothing else in this document tells it otherwise. Its description therefore states that it is the fallback for what the typed tools do not cover and names the typed tools serving the common cases; and when a query targets a table a typed tool already encodes, the response names that tool alongside the rows.

**An R13 answer inherits none of the typed tools' semantics, and the response says which ones it skipped.** A caller reading diagram connectors straight out of `t_diagramlinks` gets a clean, well-formed result missing 2,723 rows and nothing in it says so — the motivating failure exactly, reproduced through the newest tool in this plan. The server knows which tables its typed tools encode, so the response names any queried table that has one, with the correction that tool applies: `t_diagramlinks` is an incomplete index (R2), `t_connector.StyleEx` needs parsing (R1), `t_objectconstraint` holds its specification text under a reserved-word column (R10). **The set of queried tables is collected from the authorizer's `SQLITE_READ` callbacks during prepare, not by inspecting the statement text** — a substring match would fire on a table name inside a string literal or a comment and would miss one reached through a CTE, an alias or a subquery, and it is the same technique the guard rails below reject. The authorizer is already installed for other reasons and delivers exactly the read tables: a two-table join was measured producing `[20,"t_connector","Connector_ID","main",null]` and `[20,"t_object","Name","main",null]` and nothing else. This does not make the query right; it removes the reader's grounds for assuming it is. **Any typed tool added after Phase 4 registers the tables it encodes and the correction it applies**, under R0's inherited-by-later-tools clause — otherwise the mapping goes stale and R13 begins under-reporting the semantics it bypasses, which is this plan's own failure returning by drift.

**The guard rails are an allowlist, not string inspection and not a denylist.** `readOnly: true` blocks writes to the model file, `load_extension` is refused as unauthorized, and `readfile` does not exist outside the CLI shell — all three verified against this model. It does not block `ATTACH`, it does not block `PRAGMA`, and it does not block temp writes: `CREATE TEMP TABLE bomb AS SELECT a.Object_ID, b.Name FROM t_object a, t_object b LIMIT 1000000` was measured succeeding on a `readOnly` connection in 266 ms, producing 11.9 MB of `etilqs_` temp files, with `INSERT INTO` that table permitted too. It is a single statement, it is neither a `PRAGMA` nor an `ATTACH`, and it returns zero rows — so a denylist built from the two obvious action codes never sees it, and neither the row cap nor the response-size cap applies. Only the time limit bounds it, at roughly 45 MB of disk per second. SQLite's authorizer callback is therefore configured as an allowlist: it permits only the action codes a read needs — `SQLITE_READ` (20), `SQLITE_SELECT` (21), `SQLITE_FUNCTION` (31), `SQLITE_RECURSIVE` (33) — and denies every other code, including `SQLITE_CREATE_TEMP_TABLE`, `SQLITE_CREATE_TEMP_INDEX`, `SQLITE_CREATE_TEMP_VIEW`, `SQLITE_INSERT`, `SQLITE_PRAGMA` and `SQLITE_ATTACH`. Denying an enumerated list would leave every code nobody thought to enumerate open. Parsing the statement as text is not equivalent to either and should not be used in place of them.

**Those four codes were measured sufficient, not assumed.** A read-only allowlist that refuses ordinary reads is a worse failure than the temp write it prevents, and the set is small enough to look complete while being short by one. Ten representative statements against this model — a bare `SELECT`, `ORDER BY` on an unindexed column, a `LEFT JOIN`, `GROUP BY` with `COUNT`, a scalar function, `LIKE`, a recursive CTE, an `IN` subquery, a `UNION`, and a read of `sqlite_master` — all completed under the four codes, and together they triggered no code outside the set. `sqlite_stat1` and `sqlite_dbpage` do not exist in this build, so the internal tables reachable under `SQLITE_READ` are `sqlite_master` and the model's own — the same schema R12 publishes deliberately.

**`SQLITE_FUNCTION` is bounded, because permitting the code permits every built-in.** The allowlist is what makes `LIKE`, `COUNT`, `upper` and the date functions work at all, so it cannot simply be dropped; but it also admits the built-ins that allocate without reading anything. Under the allowlist above, `zeroblob(200000000)` was measured returning a 200 MB value in 1 ms, `randomblob(50000000)` in 136 ms, and `printf('%.*c', 50000000, 'x')` producing 50 million characters in 100 ms — a submission of a few dozen bytes materialising tens of megabytes in SQLite's native layer, where the response-size cap has not yet had anything to measure. The row cap never fires: each is one row.

**The bound is stated as an obligation and met by one of two mechanisms, because the better one is not available on the floor runtime.** The obligation: a caller-supplied statement cannot materialise a value larger than the server's byte budget, and a legitimate value below it is returned untouched. On the floor, the mechanism is a **denylist of allocation built-ins refused by function name** in the `SQLITE_FUNCTION` callback, which carries the name in its *third* argument — `[31, null, "upper", null, null]` was the measured callback shape, and reading the second instead silently disables the denylist while every test still passes. It refuses `zeroblob` and `randomblob` including nested inside another call such as `hex(zeroblob(10))`, with the message `not authorized to use function: zeroblob`, and leaves `upper` untouched. **It has one measured gap: `printf('%.*c', 50000000, 'x')` passes**, because the amplification lives in the argument rather than the name, and denying `printf` outright was measured to take legitimate `printf('%s-%s','a','b')` with it — the denylist is all-or-nothing per name and cannot see argument shape. Where `DatabaseSync.limits` is available the server sets `limits.length` to the byte budget instead, which bounds the *result* rather than the route to it: at 8 MB it refused both `zeroblob(200000000)` and the `printf` amplification with `string or blob too big` while returning a real 24,353-byte note unaffected, and `limits.attach = 0` refuses `ATTACH` natively with `too many attached databases - max 0`. Both mechanisms are used together where both exist. `load_extension` needs no entry in either; it was measured already refused as unauthorized.

**The rails belong to the execution path that runs the caller's SQL, and only to that path.** Two mistakes are available here and each passes a careless test. Leaving the authorizer installed on the connection the rest of the server uses denies `PRAGMA` wholesale — R12's `PRAGMA table_info` stops answering, because the authorizer distinguishes actions, not callers. The mirror image is worse: the query runs on a connection opened elsewhere, without `readOnly` and without the authorizer, while the acceptance test asserts the refusals against the server's primary connection and passes. The requirement is therefore a property of the execution path, in three parts. Every connection that executes caller-supplied SQL **is opened read-only; completes a fixed, server-issued prologue — the `PRAGMA cache_size` tuning `openDatabase()` already applies — and only then has the authorizer installed, before the first *caller-supplied* statement.** Installing it any earlier bars the server's own prologue: with the authorizer first, `PRAGMA cache_size = -64000` was measured returning `not authorized`, which leaves the one connection running unindexed caller scans without its cache. That is not free — the same both-ends join measured 10,422 / 10,928 ms at the default cache against 7,435 / 6,722 ms with the tuning applied, so dropping it worsens exactly the risk the time limit exists to bound. Third, **the caller's statement crosses the process boundary as data on a pipe or IPC channel, never as part of a command line and never through a shell**, with the query process started from a fixed argument vector; A13 asserts what SQLite refuses and would not catch caller text becoming command text. A13 asserts the refusals on this path, not on the primary connection.

This ordering is reachable through `openDatabase()` unchanged, once the query runs in a process of its own. That function opens the handle read-only, runs a sanity `SELECT COUNT(*) FROM t_object`, applies the `PRAGMA cache_size` prologue and returns — and the point between the prologue and the caller's first statement is the moment it returns. That point looked unavailable only under the assumption of one shared connection: an authorizer installed on the handle every registration in `src/index.ts` receives would deny R12's own `PRAGMA`. The query process opens its own handle through the same function and installs the authorizer after the call returns. **Neither an extension point nor a second opener is required** — the prologue is not duplicated, so the two cannot drift apart, and the server's primary connection never carries an authorizer at all.

**Unbounded execution is the remaining risk, and only a separate process contains it.** A recursive CTE counting to a million completes without complaint, and an ordinary query written without knowledge of the indexes can run for minutes against a 663 MB file. `DatabaseSync` exposes no `interrupt` and no progress handler, so a running statement cannot be cancelled in place. A worker thread was the obvious host and is ruled out by measurement: `terminate()` requested at 592 ms against a long recursive CTE resolved only at 81,214 ms, once the query had finished on its own — a limit that fires after the work completes is advisory, not enforced. **The query therefore runs in a child process, which `SIGKILL` ends in 14 ms while the statement is still executing inside SQLite's native layer**, with the parent undisturbed: 63 ms worst gap against a 50 ms nominal timer while the child burned CPU. What that costs was measured rather than assumed — spawn to ready is a median 139 ms on an idle machine, of which roughly 130 ms is Node's own interpreter startup, because opening a second read-only connection to the 663 MB export costs 0.50 ms and a first `COUNT(*)` a further 5–8 ms. SQLite reads the header, not the file. The figure is load-dependent — the same measurement repeated on a busy machine ranged 180–428 ms — which does not disturb the argument: against a limit measured in seconds, even the worst of that is noise, and it is the price of a limit that actually stops things. A query stopped by the limit is reported as stopped.

**What the query process is given, it is given explicitly.** It receives the parent's already-resolved `.qea` path rather than re-running `resolveQeaPath`, which picks the newest `.qea` by modification time — a child resolving for itself could open a *different* export than the one R11 just reported, and would do so precisely in the case that matters, a model replaced while the server was running. The authorizer-collected table set travels back to the parent alongside the rows, because the semantics notice is assembled from it; a child returning only rows cannot say which typed tool the query bypassed. **The process starts with a reduced environment rather than the server's own**, the path arriving over the IPC channel as the rule above already requires. This is not a trade: forking with `env: {}` was measured cutting the child's visible variables from 84 to 11, removing `EA_QEA_PATH` and a planted credential-shaped variable, while the connection, `LIKE`, a recursive CTE and `setAuthorizer` behaved identically and the wall time did not measurably differ. And **the process is given a temporary directory of its own**, which the reduced environment above makes a one-line matter. The allowlist stops the caller from *asking* for disk, but not from causing it: an ordinary sort — no temp table, no `PRAGMA`, no `ATTACH` — was measured under the full allowlist writing an 82.3 MB `etilqs_` file while ordering 653,040 rows of `Note` by an unindexed text column, taking 1,931 ms to produce its first row. Pointed at a private directory the same query left the inherited temp untouched, so the spill is bounded and disposable rather than accumulating in the operator's temp space. This is a resource question, not a privilege one — the rate, about 43 MB per second, is what the time limit already bounds — but nothing else bounds *where* it lands.

**The response-size cap is applied in the query process, against rows as they arrive.** Materialising the result and measuring it afterwards would let a caller at the raised row ceiling exhaust memory before the cap had anything to measure: the cap would be reported, and the failure it exists to prevent would already have happened. Streaming is available and was verified rather than presumed — `StatementSync.iterate()` over `SELECT Object_ID, Name, Note FROM t_object` returns its first row after 0.32 ms where `all()` takes 740.75 ms to materialise all 72,560; abandoning the iterator early leaves the connection usable for the next statement; and the method is declared in the pinned `@types/node` line, so unlike `setAuthorizer` it needs no augmentation. Bytes are counted as rows are appended and the walk stops when the budget is met, which is also what makes the byte figure R0 reports a true measure of what was assembled rather than of what survived.

**A missing authorizer means a missing tool, not an unguarded one.** Without `setAuthorizer` there is no sound guard left to fall back on. `readOnly: true` alone was measured against this export permitting `ATTACH`, permitting `CREATE TEMP TABLE … AS SELECT` over `t_object`, answering `PRAGMA cache_size`, and returning a 200 MB `zeroblob` — all four of the things the rails exist to stop. The only remaining option would be inspecting the statement as text, which this requirement rejects everywhere else and which would fail on the same cases. Neither a declared `engines.node` nor a raised type definition prevents the built `dist/index.js` from running on a runtime where the method is absent — npm warns on an engine mismatch rather than failing unless `engine-strict` is set, and types vanish at compile time. On such a runtime the tool would register, `ATTACH` would work, and nothing in any response would say the guard rail was gone. **The server therefore checks for `DatabaseSync.setAuthorizer` before registering R13 and, when it is absent, does not register the tool at all and reports why — in two places, because the two readers are different and only one of them can act.** The startup log tells the operator, who is the only party able to change the runtime. The server's own description tells the agent, which otherwise finds a tool that this documentation describes and this deployment does not have, with nothing to explain the gap. Reporting in one place leaves the other reader guessing, and the agent's guess is the expensive one — it reaches for a workaround, which is the behaviour this plan spent its length trying to make unnecessary. The declared Node floor is a compatibility signal, not the enforcement point. Degrading R13 instead of withdrawing it is not available: the fallback for a missing authorizer is not a weaker version of the same tool but the bounded table reader recorded as a rejected alternative in Key decisions.

**The floor is Node 24 LTS, and the type definitions are not what sets it.** `setAuthorizer` arrived in **v24.10.0** (2025-10-08) and `DatabaseSync.limits` in v25.8.0 (2026-03-03); neither is declared in the `@types/node` 22.x line this repository pins, whose coverage stops at `@since v22.18.0`. That reads as a forced choice between raising the types package-wide and asserting the type at the call site, and it is not one: **a local module augmentation declaring the two members merges into the existing class and compiles clean** — `tsc --noEmit` under `strict` with `@types/node` 22.20.0 exits zero. The augmentation is an assertion about the runtime, so the runtime check above is what carries the guarantee; it is written once, in one reviewable file, without `any`, and is deleted when the pinned types declare the members themselves. The floor is therefore chosen on runtime grounds alone. **It is `>= v24.10.0`, which is exactly "Node 24 LTS or newer"** — the first Node 24 release flagged LTS is v24.11.0 (2025-10-28), above it, so no user on the LTS line falls below the floor. Node 24 *Krypton* is the current Active LTS, in maintenance from 2026-10-20 and supported to 2028-04-30; the only line the floor excludes is Node 22 *Jod*, which entered maintenance on 2025-10-21 and ends 2027-04-30.

**Node 26 LTS is the scheduled upgrade, with a date rather than an intention.** Node 26 becomes LTS on **2026-10-28**. From that point `DatabaseSync.limits` is available on an LTS line, and raising the floor to Node 26 lets the denylist branch, its measured `printf` gap and the two-mechanism text above be deleted rather than maintained. The upgrade is therefore not speculative cleanup: it removes a known incomplete guard. It is deliberately *not* taken now, because doing so would put the floor on a Current release and exclude the only LTS line where the server can run at all. **The trigger is the LTS transition date, and the check is that R13's behaviour is unchanged by it** — the obligation is written against the observable property, so both mechanisms satisfy the same acceptance criteria and the upgrade removes code without changing what any caller sees.

**R0 applies to R13's own caps, and is not in tension with them.** A limit the caller writes into its own query is chosen and visible to the caller; the failure this plan removes is a limit the *server* imposed silently. Only the server's own caps need reporting, and R13 has three. **The row cap is raisable by the caller up to a server ceiling; the response-size cap is fixed and exposes no parameter; the time limit is fixed.** All three are reported under R0 like any other cap, which is what makes a raised-limit continuation a call the server can honour. Two details follow from the hard rule that the server never offers a call it cannot honour. The row-cap report **names the server ceiling alongside the caller's parameter, and once the ceiling is the binding cap it omits the raise-call and states that no parameter reaches further** — otherwise a caller already at the ceiling receives a call that returns the identical truncated result. And the response-size cap **reports its byte budget and the bytes returned**, so a caller meeting it can chunk a large column with `substr` itself; without that figure the cap is a dead end for exactly the content the Non-goals defer to R13 — `t_document.BinContent` averages 123,014 bytes over 2,841 rows, 334 rows exceed 100 KB, and the largest is 103,176,739 bytes, so no single-shot read reaches those rows whole. This reconciles R13 with R0 on the dimension of caps only — the other dimension, an answer that looks whole and is not, is handled by the semantics notice above and not by this paragraph.

#### Standalone

**R11. Model provenance.** A tool reports which `.qea` file answered — its resolved path, file modification time, and size. When an answer is pasted into a tracker under a claim that it was verified, the identity of the export is part of the evidence. **The citable identity is the file name, size and modification time**; that is what carries the evidentiary weight and what the tool presents for publication. The full resolved path is available alongside it, marked as local detail — in this deployment it embeds a user profile directory, and for network exports the internal share roots that appear in the model's own note links. The resolved path is available from the open connection itself — `DatabaseSync.location()` returns it — so this does not require threading the path through tool registration.

**R12. The schema is readable.** A tool lists the model's tables and, for a named table, its columns with their declared types and its indexes with the columns each one covers. This is the direct answer to the deepest problem in the table above: the motivating failure was not a missing column but an agent with no way to learn that a column existed. The indexes matter for the same reason the columns do — against 81,973 connectors, the difference between a filter on an indexed column and one without is the difference between an answer and a timeout, and a caller has no other way to tell which query it is about to write. **The listing also reports each table's INTEGER PRIMARY KEY / rowid access path, stating that SQLite does not list it among the indexes — and it reports it only where one exists.** The `pk` column of `PRAGMA table_info` gives a column's position within the primary key, not a rowid-alias flag, so `pk > 0` is the wrong test: it holds for every key column of every keyed table. Across this model's 100 tables, only 24 have the single-column `INTEGER` primary key that aliases the rowid; 45 have a single-column key of some other declared type, 22 have a composite key, and 9 have none. Reporting a rowid path on the strength of `pk > 0` would announce a non-existent fast path on 67 of the 91 keyed tables — R12's own failure mode, since its whole purpose is to stop a caller guessing what the file supports. **The test is that exactly one column carries `pk > 0` and its declared type is `INTEGER`, compared case-insensitively**; `t_object`, `t_connector`, `t_diagram`, `t_diagramlinks` and `t_diagramobjects` all satisfy it, and a table that does not is reported as having no rowid alias rather than omitted. Without that, R12 answers the question backwards for the fastest path in the file: `PRAGMA index_list` returns 223 indexes across the 100 tables — 15 on `t_object`, 12 on `t_connector`, including the composite `ix_connector_startobjidconnid` on `[Start_Object_ID, Connector_ID]` — yet `Object_ID` and `Diagram_ID` appear in neither of their own tables' lists, while `EXPLAIN QUERY PLAN` shows `SEARCH t_object USING INTEGER PRIMARY KEY (rowid=?)`. A caller trusting the index list alone would avoid the one filter it should reach for first. R12 depends on nothing else here and carries none of R13's risks: `sqlite_master`, `PRAGMA table_info`, and `PRAGMA index_list` / `index_info` all answer on a read-only connection today.

### Non-goals

- **Writing to the model.** The server stays read-only; settled, not reopened here.
- **Diagram geometry as a typed tool.** Coordinates, sizes, z-order, rendering. Position may mean something to a human reader; the mapping this plan targets lives in connectors and features, not layout. Reachable through R13 if a concrete question ever needs it.
- **Image export.** Rendering a diagram to PNG or SVG.
- **Sanitising or flattening model text.** Stripping the HTML dialect EA stores would destroy list structure and embedded model traces; see R3.
- **Tagged values as a typed tool.** `t_objectproperties` holds 387,280 rows, overwhelmingly BPMN/UML profile machinery (`auditing`, `monitoring`, `adHocOrdering`). Analyst-authored content exists but is sparse, and the sparseness is now measured rather than asserted: property names that read as prose account for 9,697 of those rows, about 2.5%, and admitting the single-word Slovak names that test misses brings it to roughly 3.4%; on connectors the analyst share is 436 rows of 94,892, or 0.5%. The named ones are `Owner` (1,620), `Stav` (1,429), `Typ` (1,196), and `Cieľový ústav` (403, on connectors) — counts of rows carrying a value, which is the narrower and the more honest figure, since `Stav` is attached to 2,289 elements and left empty on 860 of them. Not worth a dedicated tool until a concrete question needs one; reachable through R13 in the meantime. When that need arrives the filter is cheap, because the analyst-authored set is small and nameable — and that, rather than the absence of demand, is what makes the deferral safe.
- **`t_xref` and linked documents as typed tools.** 131,844 and 2,841 rows respectively, with no established need. Same treatment: no typed tool, reachable through R13 — with one qualification for `t_document`: `BinContent` averages 123,014 bytes and runs to 103,176,739, well past R13's fixed response-size cap, so a large row is reachable only in chunks the caller assembles using the byte budget R13 reports.
- **Mapping the model to source code.** The server sees the model, not the implementation repository. Translating `Vyživovaná osoba.05. Rodné číslo` into a C# member is the reader's job.

**Three of these deferrals were contingent on R13, and that contingency has expired.** Diagram geometry, tagged values, and `t_xref` / linked documents were each deferred on the ground that R13 reaches them in the meantime. With Phase 4 outside the implementation scope there is no meantime — nothing reaches them. They stay deferred, but now on their own merits alone: no established need, and profile machinery a typed tool would have to filter. What changes is the consequence of a need arriving. It is then answered by a typed tool on its own increment, rather than by waiting for Phase 4. The qualification above about `t_document.BinContent` and R13's byte budget describes how that content would be reached *if* R13 ships; until it does, it is not reachable at all, and that is the honest statement of the gap.

### Key decisions

- **Extend existing tools rather than adding parallel ones** where the data belongs to an existing concept. Feature links extend `ea_get_connectors`, diagram connectors extend `ea_get_diagram_elements`, diagram membership and constraints extend `ea_get_element`, step detail and scenario notes extend `ea_get_scenarios`. New tools appear only for genuinely new entry points — reference resolution, diagram listing, model provenance, schema reading, and the guarded query fallback. *Rationale: an agent that already reached for `ea_get_connectors` should not need to know a second tool exists to get a usable answer.*
- **Constraints belong to the element, not to its scenarios.** Attaching them to `ea_get_scenarios` was the obvious placement — steps cite constraints by name — and it is wrong: 161 elements have constraints and no scenario, so that tool would answer "none found" for content that exists. Steps cite constraints; they do not own them.
- **R0 is a requirement on every tool, not a phase.** Completeness reporting is the single behavior whose absence caused the motivating failure, and the codebase already demonstrates it in `ea_get_element`. Treating it as a cross-cutting rule keeps new tools from reintroducing the defect.
- **R0's remedy obligation is graded, not uniform.** Requiring an exact next call on every incomplete answer was considered and rejected: it is unconstructible for `ea_get_element`'s item cap, ambiguous for a clamped package depth, and meaningless for an unresolved feature link. A uniform rule would force the server to advertise calls it cannot honour. The facts the server always knows are mandatory; the exact call is required only where one continuation is correct; elsewhere a text hint is the honest answer.
- **Field origin comes from `columns()`; the table set does not.** Per-field attribution was previously recorded in R0 as requiring the server to parse its own `SELECT` lists. That was never verified and it is false: `StatementSync.columns()` returns origin table, origin column and declared type for every returned column — through joins and subqueries, for a column named with a reserved word, and without a single row being fetched. The reason to adopt it is not the attribution itself, which is uninformative wherever a tool joins a table to itself; it is that an expression reports a *null* origin, which converts `ea_search`'s `substr(o.Note, 1, 200)` from a truncation someone must remember to declare into one the server detects. What `columns()` cannot do is name a table that no returned column came from — a statement selecting only an aggregate attributes to nothing while having read a table in full. A mechanism that under-reports cannot be the source of a completeness claim, so the table set keeps its own and this one is confined to fields. The relationship between the two is one-directional and therefore testable: every table `columns()` names must appear in the declared set, and a join added without updating that declaration fails. The assertion belongs in the Verification Contract, not in the response.
- **`ea_get_element`'s item cap is raised rather than paged.** Measured instead of argued: of 15,877 elements carrying attributes, 17 exceed the 50-item cap; of 5,450 carrying operations, one does. The median element has 3 attributes and 2 operations. A paging parameter would therefore be designed for 18 elements out of 72,560 — while the cap it exists to work around silently truncates exactly the elements a reader looks up, `Klient` at 76 attributes and `Výstup` at 77. Raising the inline cap past the 170-attribute maximum removes attribute truncation from the model entirely, at a cost of a few hundred extra rows on 17 elements. The cap itself stays, because one outlier keeps it meaningful — an interface carrying 1,104 operations — and it reports itself under R0 as before. No paging parameter is added.
- **Connector roles are returned; `Btm_Mid_Label` is not.** Both were recorded as unverified and both were measured. `SourceRole` (1,552 non-empty) and `DestRole` (3,284) are a mixture: 48% and 40% respectively are physical data-model key names carried over from reverse-engineered schemas (`FK_PDD_KLIENT`, `..._id_pk`), and the remaining majority is analyst naming that appears nowhere else — `Člen komisie`, `navedomie`, `zaevidoval`, `Cela po DT`. Two columns is a small price for the half that carries meaning. `Btm_Mid_Label` is the opposite result: 31,644 non-empty rows hold only 87 distinct values, 86% of them identical to the connector's own `Stereotype` once rendering whitespace is stripped, and every remaining row restates `Connector_Type` instead — `«use»` on a Usage, `«flow»` on an InformationFlow. It is the caption EA draws, derived from data the tool already returns, so returning it would add volume without adding a fact.
- **One resolver instead of three lookups.** GUID, path, and name lookups share a return shape and a disambiguation problem; they are one capability with three input forms.
- **`Notes` on a resolved feature is part of the payload, not an optional detail.** The attribute code alone (`a7782`) is not actionable; `a7782 ("Rodné číslo")` is. That is the difference between returning data and returning an answer.
- **Model text stays HTML; the server declares the type rather than normalising it away.** Stripping markup was considered and rejected on evidence: list structure carries distinct requirements, and anchors carry model traces and legal references. The danger is not the markup — it is a field whose encoding is undeclared and whose escaped literals get decoded by a blanket transform.
- **`ea_search` matches over a folded corpus held in memory, built on the first search.** Four substrates were measured on this export; the table and the method are in Provenance. Today's `LIKE` is wrong on every query tested. A full scan per query is correct and costs 659–978 ms *every* time. The in-memory corpus costs 765 ms once and 12–14 ms per query, at 155 MB resident — a figure that belongs to the record shape that benchmark used and not to the substrate, as the re-measurement in Provenance shows. A temp table carrying an FTS5 trigram index is the fastest per query (0–7 ms) and is still rejected for now: it costs 5,421 ms to build, which buys back roughly 11 ms per query and so needs on the order of 420 searches in one process to pay for itself, against sessions that run to tens. Building at startup instead of on first search was rejected on the same arithmetic moved earlier — it charges every session, including those that never search.
- **What would switch `ea_search` to the trigram index — and, measured, what would not.** Three things were expected to decide this and none of them survived measurement at the scope actually adopted. **Memory does not decide it:** the folded corpus holds 172 MB and the trigram index 166 MB over identical text, so the projection that a tripled corpus drives the in-memory option toward 450 MB while the index stays near 82 MB is wrong, and at the narrower scope the same pair comes out at 45 MB against 37 MB. **Semantics do not decide it:** the trigram tokenizer declared `remove_diacritics 1` returned counts identical to the folded corpus on every term tried, including ten arranged as with-and-without-diacritic pairs of the same Slovak word. **And the index needs nowhere to live:** `CREATE VIRTUAL TABLE` inside the export is refused with `attempt to write a readonly database`, but the same statement against the `temp` schema of that same read-only connection succeeds, so there is no sidecar file and no cache that can go stale against the export's mtime. What remains is one trade. The index costs 4.9–7.2 s more to build and saves 21–35 ms per query, paying for itself after **208 to 231 searches in a single process** — a break-even that held within a tenth across runs whose build times differed by half under machine load. That observed number, not a projection, is the trigger. Two findings are recorded so the switch does not rediscover them: FTS5's *trigram* tokenizer is required rather than FTS5 generally, since the ordinary tokenizer matches token prefixes, loses four to five hits per term and returns 0 of 168 for an infix; and the trigram tokenizer silently returns zero for terms shorter than three characters, so a scan fallback below that length is part of the work rather than an afterthought. The plain `LIKE` form of the same idea is *slower* than the JavaScript scan — 58–107 ms against 12–14 ms — so the index is the entire benefit and a temp table on its own is a regression.
- **The folded corpus covers scenario text, constraint notes, and attribute and operation names and notes — not `t_object` alone.** R3 names that text and Phase 3 inherits R3, so a corpus built from `Name` and `Note` would leave `ea_search` unable to find content the tools are required to return, which is this plan's own failure mode turned inward. The extension takes the corpus from 95,669 entries to 234,307 and the median query into the mid-twenties to mid-forties of milliseconds, invisible inside an MCP round trip. It was expected to be the thing that forces the trigram index; it is not, because memory came out at parity. **One correction to how this was first written: `t_objectscenarios.Scenario` is the scenario's *name*, not its text** — 4,739 rows totalling 0.1 MB, a median of 27 characters. The body an analyst would search for is the step names inside `XMLContent`, **2.03 MB across 16,861 steps**, and it belongs in the corpus for the reason the rest of this entry gives: R8 requires the tools to return those steps, so `ea_search` must be able to find them. R8 parses that XML regardless, so the corpus adds no new parsing, and the addition is bounded — roughly 7% more entries and 2 MB more text than the 234,307-entry corpus the benchmark above was run against, which was measured before this correction and has not been re-run.
- **A folding function called from SQL was the fourth substrate, and it fails on this model before speed becomes the argument.** Registering the plan's own NFD-strip-lowercase fold as a SQLite function and writing `WHERE nrm(Name) LIKE ?` is semantically identical to the corpus — same folding, same answers — which is why it earns a recorded refusal rather than a dismissal. Written the way it is normally offered, without a null guard, it throws on the first query against this export: `Note` is null on 43,414 rows and `Name` on 6,037 of 72,560, and `null.normalize` raises. Guarded, it is correct and `EXPLAIN QUERY PLAN` reports `SCAN t_object` even with the function declared deterministic, because a function of a column cannot be served by an index on that column. Over six terms it costs a median 333 ms against 41 ms for the in-memory corpus on identical text, since the fold is recomputed for every row on every query rather than once per process — the same work at the wrong time. One property is genuinely better and is recorded so the option can be reopened honestly: it holds no memory at all, against the corpus's 172 MB, and it needs no build step. Neither is binding here. Whether that last property makes it worth exposing inside R13's query process, where a caller writing ad-hoc SQL has neither corpus nor index available, is a Phase 4 matter and is not decided by this bullet.
- **The substrate is not a startup parameter.** Offering folded-corpus-against-trigram as an option in `mcp.json` was considered and rejected on the measurements rather than on principle. A parameter earns its cost when it lets someone choose an outcome they can evaluate, and this one changes no outcome a caller can observe: both substrates return identical counts on every term tested, and both hold the same memory to within four percent. All it would expose is the startup-against-query trade, whose break-even sits above two hundred searches in one process — and whoever edits `mcp.json` cannot know in advance how many searches a session will make, while being wrong either way costs a handful of seconds. This is the rule already applied to the missing-authorizer report: a choice belongs to whoever can act on it, and here that is nobody. Building the index lazily in the background would collect both halves and is the reasonable answer if this is ever reopened; it is not worth building while both options are acceptable.
- **Long text is retrieved by the call R0 already names, and no new shape is added for it.** Three were open — a dedicated call, a parameter on the existing one, a raised default — and measurement removes the need for all three. Across 29,146 element notes the median is 150 characters, the 99th percentile 2,614, and the longest in the entire export 24,353; two exceed 16 kB, none exceeds 64 kB, and every note in the model together comes to 9.0 MB. Scenario text tops out at 206 characters, constraint notes at 3,894, attribute notes at 16,053. Nothing here needs paging. The server's only truncation of text is `ea_search`'s 200-character `NotePreview`, which exists to keep a result list readable rather than to bound a payload, and R0 already classes its continuation as a level-2 case resolved by `ea_get_element` on the id being returned. What the measurement does oblige is the level-1 half: the preview carries an explicit truncation flag rather than leaving the field name to imply one.
- **R0's source-table declaration binds every tool, with no carve-out for narrow reads.** The exemption considered was for tools whose unreturned column set is small enough not to mislead. No such tool exists here. `ea_get_connectors` returns 17 of `t_connector`'s 79 columns, `ea_search` 10 of `t_object`'s 57, `ea_get_element` 14 of those 57 alongside 9 of `t_attribute`'s 27 and 6 of `t_operation`'s 27, `ea_get_diagram_elements` 6 of `t_diagram`'s 29, and `ea_get_package_tree` 3 of `t_package`'s 23 — between 67% and 87% unreturned in every case, with only `ea_get_scenarios` lower at 4 of 7. A rule discriminating by width would have to draw its line inside a band the data shows no gap in, so the obligation is uniform and the exemption is not written.
- **A link target found in note markup is resolved when its scheme keeps it inside the model, and is never fetched.** R3 surfaces these targets and R0 declares the surrounding text untrusted, which left open whether same-model provenance is enough to act on one. The scheme settles it, because the scheme is the part that states where the target lives. Across 1,799 `href` targets in 1,111 notes, 1,467 are `$element` and resolve to a row in this export 97.3% of the time, with `$diagram` (34, resolving 88.2%), `$package` (17), `$feature` (4) and `$matrix` (4) behind them; 158 leave the model altogether — `$inet` 82, `https` 63, `http` 9, `file` 4 — and 115 are relative. Resolving the first group is a GUID lookup in the file the server already has open, reaching nothing the caller could not reach by asking directly; provenance is not what makes that safe, the absence of any reach is. The second group is never followed, and the server does not become an HTTP client on the strength of a string an analyst typed. A first-group target that does not resolve — 2.7% of `$element` — is reported present-but-unresolved under R0 rather than dropped.
- **The path form is admitted on measurement, and the reasoning that had excluded it is withdrawn rather than quietly dropped.** This document previously held that no matching rule could reach a dotted path, on the ground that 815 of the 1,308 dotted package names are ordinary abbreviations nothing distinguishes from a separator. That observation is correct; the conclusion did not follow from it, because it assumed the resolver must split the string on `.` — which a resolver matching against the tree's real names never does. Measured, the backtracking match recovers the true node from its own canonical path in 800 of 800 cases and identifies it uniquely in 78.1%, with the caller's declared kind collapsing 99% of what is left. The withdrawn claim is recorded because it was the sole reason the form sat outside the first increment, and because a wrong conclusion drawn from correct facts is the failure this plan is least able to detect by review.
- **No SQL-side matching may join columns with a NUL.** Where several columns are folded into one searchable string, the separator cannot be `\0`: SQLite's `LIKE`, `GLOB` and `length()` all stop at an embedded NUL even though the bytes are stored whole, so the value is present, the index sees it, and the comparison does not. It produces answers that are short and confident, which is this plan's defining failure. Recorded because the benchmark that produced the numbers above walked into it first and only caught it on a parity check.
- **Slovak ordering is done in JavaScript, and it cannot be done in SQL at all.** SQLite's only case-insensitive collation folds ASCII and nothing else: measured on this runtime, `'A' = 'a' COLLATE NOCASE` is true while `'Č' = 'č'`, `'Š' = 'š'`, `'Ľ' = 'ľ'` and `'Ž' = 'ž'` are all false. No configuration reaches that. There is no `CREATE COLLATION` statement in SQLite — the form is a syntax error, not an unsupported feature — `node:sqlite` exposes no collation registration on `DatabaseSync` at all, and the ICU extension that would supply one is not compiled into the shipped build. The two places this would do real damage were checked rather than assumed, and both are clear: R1's `ea_guid = ? COLLATE NOCASE` is unaffected because braced hex is ASCII, and search is unaffected because folding happens in JavaScript before anything is compared. Where it lands is `ORDER BY`, which four tools already use on a name column. Binary collation orders by code point, so SQLite returns `Cena Dôvod Sudca Ulica Zákon Čas Ďalej Škoda Žiadosť` where Slovak order is `Cena Čas Ďalej Dôvod Sudca Škoda Ulica Zákon Žiadosť` — every accented initial sorts after `Z`, affecting 2,570 element names and 398 package names, 3.9% and 3.8% of each. The effect is narrower than that sounds and the reason is worth stating: in all four tools `Name` is a *secondary* key, behind `Connector_Type`, `Object_Type`, `TPos` or a relevance `CASE`, so the misordering happens inside each group rather than across the whole result — which is precisely why it reads as a plausible list rather than a broken one. Ordering is therefore applied after retrieval with `Intl.Collator('sk')`, measured at 0.71–1.53 ms per 500 names against result sets that are bounded by construction. The rejected alternative is a folding function inside `ORDER BY`: it works, and it forfeits any index on the sorted column for the same reason the `UPPER()` form of R1's lookup does. *Rationale: a wrongly ordered list is a completeness failure that R0 cannot catch, because nothing is missing from it.*
- **Feature-link parsing is tolerant.** `StyleEx` is a semi-structured style string; an unparseable token degrades to object-level output *and says so*, rather than erroring or silently vanishing.
- **Phases are ordered by what they unblock, not by which table they touch.** Phase 1 makes existing answers correct, Phase 2 makes them reachable, Phase 3 opens the second citation shape, and Phase 4 reaches what the typed tools do not cover.
- **Phase 3 goes third despite serving an equally common need — the tiebreaker is the class of damage.** Demand does not separate the two citation shapes. What separates them is how each fails today. Phase 1 removes *silent incorrectness*: `ea_get_connectors` returns an answer that looks whole and is not, so a reader has no signal to doubt it, and the motivating case ended in a false published claim. Phase 3 removes *visible absence*: `ea_get_scenarios` already returns the step text, and a step naming a constraint the server cannot supply reads as an open question rather than a finished answer. Under the project rule that forbids asserting what was not read, the first failure produces wrong statements and the second produces missing ones — so the first is fixed first. Phase 3 also inherits R3, so it cannot lead outright.
- **What would promote Phase 3.** A case where the constraint gap causes a *wrong* answer rather than an incomplete one — a step whose text reads as self-contained but whose named constraint reverses or narrows it, such that acting on the step alone implements the wrong rule. That converts Phase 3 into the same damage class as Phase 1 and the ordering no longer holds.
- **The typed tools are the answer, and the raw query is the admission that they will never be the whole answer.** R13 was initially rejected on the grounds that a caller-written query undermines R0. That reasoning was wrong and is recorded here so it is not repeated: a cap the caller writes is chosen and visible, while the failure this plan removes is a cap the server imposed and left no trace of. The genuine cost of R13 is narrower — per-table semantics stop being encoded once. `t_diagramlinks` is an incomplete index, `t_objectconstraint."Constraint"` is a reserved word, `StyleEx` needs parsing; a typed tool absorbs each permanently, while an ad-hoc query re-derives them and can get them wrong with no sign in the result. That is a reason to keep adding typed tools, and a reason R13 must name the tables whose semantics it bypassed — not a reason to withhold the escape hatch.
- **A bounded table read was the alternative, and rejecting it was not free.** The narrower option is a primitive that reads from an allowlisted set of tables with an equality filter on an id column, server-imposed caps, and no statement text from the caller at all. It needs no authorizer, no separate process, and no Node floor — three of the risks R13 carries would simply not arise. What it cannot do is the thing R13 exists for: an unanticipated question is unanticipated in its shape as well as in its table, and a join, an aggregate, or a `LIKE` over a column nobody allowlisted is exactly what a caller reaches for once the typed tools have already failed. A bounded reader would need extending every time it fell short, which is the typed-tool treadmill under another name. R13 is chosen on that ground, with its guard rails as the price.
- **R13 reaches two deferred areas ahead of any typed tool, and the phase order does not price that.** The moment Phase 4 lands, tagged values and `t_xref` are readable, ahead of any tool at all. (`t_objectconstraint` is not among them: R10's typed tool ships in Phase 3, before Phase 4 exists.) The stated ordering principle is what each phase unblocks, with the genuinely new risk surface last; that still holds for *building*, because R13 is built last. It does not hold for *access*, because the escape hatch reaches everything at once. The consequence, accepted knowingly: any typed tool that follows Phase 4 will be replacing a working path rather than opening a closed one, and will have to justify itself on correctness rather than on capability.
- **R12 keeps its index listing in the first increment, over an objection worth recording.** The index and rowid information serves a caller writing its own query, and no such caller exists before R13 — the typed tools compose their own SQL — so the argument for moving it to Phase 4 is real, and A12's motivating-failure story closes on tables and columns alone. It stays because `PRAGMA index_list` / `index_info` are the same family of calls as `PRAGMA table_info`, which R12 already makes: the scope grows in text, not in materially new work, and splitting one small requirement across two increments costs more coordination than it saves.
- **Tests run against a generated file — never `:memory:`, and never the real export.** Both exclusions are deliberate and they rest on different grounds. `:memory:` goes because production never opens it, and because `location()` and cross-connection visibility — the two things R11 and A13 assert — do not exist there at all. The real export goes because a suite that needs a 663 MB file on disk cannot run in a CI pipeline, and one that passes only on the machine holding that file is not a verification contract. What follows from excluding both is the part worth stating plainly: the fixture becomes the only place the model's awkward shapes can exist, so reproducing them is the fixture's purpose rather than a later refinement of it.
- **R13 states obligations; its mechanism lives in this list and in Outstanding questions.** The requirement text had grown to prescribe an execution host, specific action codes and type-definition versions — implementation detail in an artifact declared `requirements-only`, and roughly the length of all four Phase 1 requirements combined. It is trimmed to what is observable and assertable: what is refused, what the caps are, what the response reports, that the time limit is enforced somewhere terminable, and that a missing authorizer means a missing tool. The reasoning behind each — why a child process rather than a worker, why an allowlist rather than a denylist, what the Node floor costs — sits here and in Outstanding questions, where every other requirement's mechanism sits. The measurements stay attached to the reasoning, because without them the choices read as arbitrary.
- **The typed-tool semantics registry is enforced by a test, not carried as prose.** R13 obliges every later typed tool to register the tables it encodes, so that an R13 answer can name the semantics it bypassed. Written as an instruction in this document, that obligation decays the first time someone adds a tool without reading it, and the decay is invisible — R13 keeps answering, just with a shorter notice. Written as a test asserting that every registered tool's tables appear in the mapping, it cannot decay silently. The obligation is therefore a line in the Verification Contract rather than a paragraph here. *Rationale: this plan exists because a tool answered incompletely without saying so; an under-reporting semantics notice is that same failure, reintroduced through the mechanism built to prevent it.*
- **The query process is not privilege-separated, and the reason is that separation would buy nothing here.** It holds the same token as the server that already opened the model file, so it reaches no further than the process that spawned it; the eleven environment variables Windows injects regardless of `env: {}` — `USERNAME`, `USERPROFILE`, `LOGONSERVER` and eight more — disclose the account, which is the same disclosure R11 already handles by marking the resolved path as local detail. What would justify a restricted token is a way for caller SQL to reach the filesystem, and under the allowlist there is none: `ATTACH` and `load_extension` are refused, `readfile` does not exist outside the CLI shell, and `PRAGMA` never reaches the parser. Requiring operators to provision a service account for a locally installed developer tool would be a real cost against a benefit nobody can name. **What the caller can still cause is disk consumption, and that is answered by the private temporary directory and the time limit rather than by privileges.** *Rationale: the same reasoning would reverse the moment a SQL-reachable filesystem verb appeared — so what is written here is the argument, not just the conclusion.*
- **The floor is the newest LTS that can run the tool at all, not the newest runtime that runs it best.** Node 24 LTS carries `setAuthorizer` and therefore the whole allowlist; Node 26 additionally carries `DatabaseSync.limits`, which closes a measured gap in the allocation bound. Taking Node 26 now would buy that gap closure at the price of a floor on a Current release, excluding the only LTS line the server could otherwise run on — a worse trade for a tool whose users install it into their own environments. The gap is instead carried explicitly, in the requirement text and in Outstanding questions, with a dated trigger for removing it. This is also why the allocation bound is written as an obligation rather than as a mechanism: two runtimes satisfy it differently, the acceptance criteria do not distinguish them, and the upgrade is a deletion rather than a behaviour change. The same shape would not have worked for the authorizer, where no second mechanism exists — which is why that one sets the floor and this one does not. **The raise itself is a dated follow-up, not an increment of this plan.** It is scheduled for the Node 26 LTS transition on 2026-10-28, it deletes the denylist branch and the local type augmentation rather than changing behaviour, and its check is that R13's observable behaviour is unchanged by it. The augmentation may go earlier and independently, whenever the pinned `@types/node` line declares the members itself. Carrying either as an open question would imply the plan waits on an answer that no part of the plan depends on.

- **R13 is decided by measurement, not by a dated review.** The eval harness (16/16 tool-level, 29/29 agent-level on the 663 MB ZVJS export) produced no instance where a typed tool's coverage gap caused a wrong or incomplete answer. When a targeted test asked the agent for a tagged value (`Stav` on DRF-01041, stored in `t_objectproperties`), the agent correctly reported it could not reach the value, identified the table and columns via `ea_get_schema`, and proposed extending `ea_get_element` — the typed-tool remedy the plan predicts, not raw SQL. R0 + R12 together produce an informed gap report instead of the silent failure the plan exists to remove. **R13 moves to Non-goals.** The column-coverage gap (67–87% unreturned in covered tables) is real but is closed by targeted typed tools (tagged values, glossary) on their own increments, not by a guarded query. If a future eval run or production use reveals a case where no typed tool can answer, R13 reopens on its own increment.

**A2 — the second citation shape.** Given the reference `UC_FEO_2027 krok 2`, an agent returns that step verbatim — *"Systém zobrazí všetky záznamy spisov podľa vypočítavanej hodnoty Dátumu vyradenia spisu podľa constrains: Spis má dátum vyradenia podľa lehoty."* — together with the constraint it names and the use case's `Process` rules, including the `LOG_FEO_083` logging rule.

**A3 — completeness is visible and actionable.** A search matching 1,580 elements reports that it matched 1,580, returned 25, and carries the exact call that raises the cap. An element whose note runs past the inline limit is marked truncated and carries the exact call that returns the full text. An element with more than 50 attributes reports the cap and states that no typed-tool parameter currently reaches the rest — it does not offer a call that would fail, and it does not offer a SQL query in place of one. That same search declares its note field as a derived value rather than the stored column, and the declaration is generated from the statement rather than written by hand, so a tool that begins computing a field without saying so does not pass.

**A4 — no feature link.** A connector with no `LFSP`/`LFEP` token returns today's shape plus null feature fields, and no existing consumer breaks. A connector with a token that fails to resolve is distinguishable from one that has none.

**A5 — discovery without a GUID.** Starting from the element name `a7680` alone, an agent finds the diagram it appears on and reads the same mapping as A1.

**A6 — search survives both encodings.** A search for `právnická` finds elements whose `Note` stores `Pr&#225;vnick&#225;`, and a search for `PRÁVNICKÁ` finds the same elements as `právnická`. The fragment `vnick` finds those elements too: the contract is substring matching, and that is the assertion which separates the chosen substrate from an ordinary full-text index, which returns nothing for it.

**A7 — escaped text survives.** An element note containing `&lt;&lt;modul&gt;&gt;` or `Dátum spracovania &lt;&gt; null` still contains them after R3 — the literal text is intact when the field is rendered as HTML.

**A8 — links are reachable, and classified.** An element note containing `<a href="$diagram://{GUID}">` yields that diagram as a structured link target, resolvable by R5 without the reader parsing markup. A note containing an `$inet://` or `file://` target yields it marked external and unresolved, so the consumer can tell at a glance which targets the server stands behind. Emitting the classified target is Phase 1 and verifiable there; resolving it is a separate step under R5.

**A9 — disambiguation.** A name-based lookup matching several same-named nodes returns them all, each with a package path sufficient to tell them apart.

**A10 — an ambiguous step citation stays ambiguous.** *krok 2* against a use case that has a Basic Path and at least one Alternate path returns both steps, each labelled with its scenario name and type. The reader chooses; the tool does not silently return the basic path alone.

**A11 — constraints without scenarios.** An element carrying constraints but no scenario returns those constraints. The reader does not have to already know that `ea_get_scenarios` would have answered "none found" for a different reason.

**A12 — the unknown column becomes findable.** An agent that suspects a connector carries more than the typed tool returns lists `t_connector`'s columns, sees `StyleEx` among them, and reads the table's indexes alongside. That alone closes the motivating failure at its root: the agent learns the model holds the answer without asking a human. Reading the values is a separate step under a separate requirement — R12 is complete, and verifiable, without R13.

**A13 — the escape hatch is bounded, on the path that runs the query.** Against the connection that executes caller SQL — not the server's primary connection — a query attempting `ATTACH` or a `PRAGMA` is refused, and so is a single-statement temp write such as `CREATE TEMP TABLE … AS SELECT …`, which `readOnly` alone permits, and so is a call to an allocation built-in such as `zeroblob` or `randomblob`. An ordinary read is *not* refused: a `LEFT JOIN` with `GROUP BY`, an `ORDER BY` on an unindexed column, a `LIKE`, a recursive CTE and a subquery all return their rows on this path, which is what distinguishes the allowlist from a connection that simply refuses everything. A submission containing two statements is refused outright, naming the trailing text, rather than executing the first and discarding the second — including when the separating semicolon is preceded by one inside a string literal, and excluding the case where the tail is only whitespace or a comment. A query that would run past the time limit is stopped and reported as stopped, not left running. A result past the row cap reports the cap, the caller's parameter and the server ceiling, and carries the call that raises it — except when the ceiling is already the binding cap, where it reports that no parameter reaches further and offers no call. A result past the response-size cap reports that cap, its byte budget and the bytes returned, and that no parameter raises it. A query reading `t_diagramlinks` returns its rows together with a notice that `ea_get_diagram_elements` corrects an incompleteness in that table, with the table set taken from the authorizer rather than from the statement text. On a runtime where `setAuthorizer` is unavailable the tool is absent from the tool list, with a stated reason, rather than present and unguarded. **The same assertions pass on the floor runtime and on one carrying `DatabaseSync.limits`**, since the oversize refusal is asserted as an outcome rather than as a mechanism — with the single documented exception that `printf` amplification is refused only where `limits` is present. Meanwhile R12's `PRAGMA table_info` still answers, and the query connection still receives its `PRAGMA cache_size` prologue.

None. The last one to close was whether R13 answers a demonstrated need or an anticipated one, and it is recorded as a decision below rather than deleted, because what settled it was a rule about evidence rather than evidence itself.

- **Whether R13 answers a demonstrated need or an anticipated one.** The motivating case is answered by R6, not by R13, and no instance has yet been recorded where a reader lost content that no typed tool returns. ### How this work fits together

Phase 1 makes the answers the server already gives correct and honest. It also delivers more discovery than its position suggests: `ea_search` already finds an element by name, and R4 turns that element into the diagrams it appears on — which is exactly the A5 path. What Phase 1 cannot do is resolve a GUID, a dotted path, or a diagram by name, and that is the precondition Phase 2 removes.

Phase 3 opens the second citation shape. In ordinary development the two are reached for about equally often — that is a practitioner's observation, not a measurement; nothing in the model counts how often a reference is *cited*. Phase 3 is additive with respect to Phases 1 and 2, but **not free-standing: it inherits R3.** Constraint notes and scenario XML carry the same character entities as element notes — 614 of the 3,783 constraint rows and 459 of the 4,739 scenario blobs contain `&#` — so R3 must ship with or before Phase 3, not merely at some point in Phase 1.

R11 sits outside all four phases and depends on none of them, but it is worth pairing with Phase 1, because Phase 1's output is what gets pasted into a tracker under a claim of verification. R12 sits outside them too, and is worth doing first of everything: it is a few lines against `sqlite_master` and the schema pragmas, it needs nothing from any other requirement, and it addresses the motivating failure at a deeper point than any single requirement here — an agent that can see the schema discovers that a column exists instead of concluding the model does not hold the answer.

Phase 4 is the admission that the typed tools will never cover everything. R13 is the one piece of this plan that adds a genuinely new risk surface rather than removing one, so it goes last, after the guard rails it depends on are built — and it is the only requirement here that moves the repository's runtime floor.

R0 is the thread through all of it. It is also the acceptance criterion for work not yet imagined: any tool added later inherits it.

The test fixture in [test/helpers/test-db.ts](../../test/helpers/test-db.ts) does not model the columns and tables these requirements depend on, and the gap is not uniform across phases:

- **Phase 1** — `StyleEx` on `t_connector`, the `t_diagramlinks` table, and `ea_guid` on `t_attribute` and `t_operation`. Extending the fixture this far is a prerequisite for Phase 1, not a separate concern.
- **Phase 2** — `ea_guid` on `t_object`, `t_package`, and `t_diagram`.
- **Phase 3** — the `t_objectconstraint` table.
- **Phase 4 and R11** — not more columns but a different substrate. The current fixture opens `new DatabaseSync(":memory:")`, where `location()` returns `null` and a second connection to `:memory:` sees none of the first one's tables. R11 cannot be asserted against it at all, and A13's refusals cannot be asserted on a second connection or in a child process, which is precisely the execution path R13 requires them on.

**The fixture becomes a file the tests write, and `:memory:` is dropped rather than kept alongside it.** Each fixture is created with `mkdtempSync` and a generated `.qea`, which is what [test/database.test.ts](../../test/database.test.ts) already does; [test/helpers/test-db.ts](../../test/helpers/test-db.ts) changes to match instead of remaining a second shape. The cost was measured and is not a factor — a fixture is built once per test file in `beforeAll`, there are three test files, and the difference is 43 ms against 7 ms, so under a tenth of a second across the suite. The reason to drop `:memory:` is that `openDatabase()` never receives it in production, so any test running there exercises a substrate the server does not have. Keeping both would additionally require a per-test judgement about which applies, and that judgement fails silently when wrong: a test that should have caught file-only behaviour simply passes. It is the same drift objection this plan already raises against a second `openDatabase()` opener, and it is no more acceptable in tests than in source. One helper owns opening and closing, including the second connections a test opens for A13 — on Windows an unclosed handle makes teardown fail with `EPERM`, which is why the existing cleanup is already written defensively.

**No test may require a real export to be present.** The fixture is code: schema and seed data in TypeScript, the file generated at run time, nothing binary committed. The immediate reason is that the suite has to run where the export does not exist, such as a CI pipeline. The consequence is the one that shapes the work: because the tests will never see the real model, the shapes this plan measured in it exist nowhere else, so the fixture has to carry them deliberately — a note storing `Pr&#225;vnick&#225;`, an element name with an uppercase Slovak diacritic, a diagram whose implied connector is absent from `t_diagramlinks`, two diagrams sharing a name, a `StyleEx` carrying an `LFSP=` token, and a table whose single-column primary key is not `INTEGER`. A fixture that merely satisfies the schema would pass every test in this plan while proving nothing about the failures that motivated it.

### Key Technical Decisions

KTD1. **Text handling as a shared module** (`src/text.ts`). Entity decoding, case folding, markup-type declaration, and link extraction are exported as pure functions consumed by every tool returning model text. Decoding is applied at response time per tool, not at storage or query time. *Governs R3.*

KTD2. **Folded corpus is a lazy singleton.** Built on first `ea_search` call, not at startup. The corpus covers `t_object` Name/Note/Alias, `t_attribute` Name/Notes, `t_operation` Name/Notes, `t_objectscenarios` step names (from XMLContent), and `t_objectconstraint` Notes — 234,307 entries at the adopted scope. First search costs ~1.4s; subsequent queries 25–45ms. *Governs R3.*

KTD3. **R0 completeness is a response-shape convention, not middleware.** Each tool composes its own `_meta` object carrying `sourceTables` (declared at registration, not runtime-derived), `totalMatched`, `returned`, `truncated`, and `continuation` (a `{ tool, arguments }` object when constructible under R0's graded obligation). Field-level origin uses `StatementSync.columns()` at prepare time to detect derived vs. stored fields. *Governs R0.*

KTD4. **File-based test fixture replaces `:memory:`.** Each test file creates a `.qea` in `mkdtempSync` during `beforeAll`, seeded with the model's awkward shapes: entity-encoded notes, uppercase Slovak diacritics, `StyleEx` tokens with trailing letters, missing `t_diagramlinks` rows for implied connectors, duplicate names across packages, reserved-word columns (`"Constraint"`), and `ea_guid` columns. `afterAll` closes connections and removes the temp directory. *Rationale: `location()` returns null on `:memory:`, multiple connections see nothing, and the fixture must exercise the shapes this plan measured.*

KTD5. **Package path as a shared utility** (`src/package-path.ts`). `buildPackagePath(db, packageId)` walks `t_package.Parent_ID` using a preloaded package map memoized per database connection. Used by R4, R5, R6, R7, and any tool reporting package context. *Governs R6.*

KTD6. **One resolver, three input forms.** `ea_resolve` accepts a `reference` string and optional `kind` filter. Form detection (braced GUID, dotted path, plain name) is internal. The dotted-path form matches against real package names rather than splitting on `.`, per the decision in Key decisions. *Governs R5.*

KTD7. **Link target classification is closed by default.** `$element://`, `$diagram://`, `$feature://`, `$package://` → model-internal (resolvable by R5). Everything else → external (returned as-is, never followed). An unrecognised scheme classifies as external, not as unclassified. *Governs R3.*

KTD8. **Slovak ordering applied after retrieval.** `Intl.Collator('sk')` sorts results in JavaScript after the SQL query returns. SQLite cannot collate Slovak — verified, not assumed (see Provenance). Affects `ea_list_elements`, `ea_get_connectors`, `ea_search`, `ea_list_diagrams`. *Rationale: wrapping the sorted column in a function forfeits the index.*
